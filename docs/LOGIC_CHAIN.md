## 1. Nine-Step Student Idea Development Framework

### Step 1 — User
**upay's growth and marketing team** — the people responsible for converting dormant registered users into Monthly Active Users (MAU) through targeted promotional campaigns within a fixed budget.

### Step 2 — Problem
In Bangladesh, competitors dominate peer-to-peer (P2P) "Send Money" due to network effects. As a result, many registered upay users remain **dormant** or **cash out 100% of their balance immediately on payday**. Mass promotional campaigns waste budget on users who would transact anyway ("Sure Things"), annoy fatigued users into muting notifications ("Sleeping Dogs"), and fail to reach the users whose behavior would actually change because of the offer ("Persuadables").

### Step 3 — Why Now
upay holds regulatory licences for **solo-utility transactions** that do NOT require the recipient to use upay:
- **Utility Bill Pay** (DESCO, DPDC, Titas Gas, WASA, etc.)
- **Mobile Recharge** (Grameenphone, Robi, Banglalink, Teletalk)
- **Super Shop QR Payments** (Shwapno, Agora, Meena Bazar)
- **Traffic Fine / Flyover Toll** (Dhaka Elevated Expressway, Padma Bridge)
- **DPS Savings** (scheduled micro-savings)

These solo-utility use cases bypass the P2P network-effect barrier. A dormant user can start a utility bill payment habit without needing anyone else to adopt upay. This is the strategic wedge.

### Step 4 — Solution
**upay ActivateAI** — a lifecycle orchestration and uplift optimization engine that:
1. **Diagnoses** why each user is inactive (lifecycle stage classification).
2. **Predicts** which solo-utility offer will trigger a 30-day repeat transaction habit (next-best-offer matching).
3. **Estimates** whether the user will activate *specifically because of the offer*, not merely *correlated with receiving it* (causal uplift modeling via T-Learner).
4. **Prevents** notification spam by detecting and suppressing fatigued users (offer fatigue scoring).
5. **Optimizes** a fixed marketing budget by targeting only users with positive incremental impact (budget optimizer with greedy knapsack).
6. **Explains** every recommendation with traceable SHAP feature attributions and bilingual (Bangla + English) SMS copy generated by Gemini 2.5 Flash.
7. **Requires** human approval before any campaign is dispatched.

### Step 5 — AI Role
| AI Component | What It Does | What It Does NOT Do |
|---|---|---|
| **LightGBM T-Learner** (two models) | Estimates P(activate \| treated) and P(activate \| control) to compute incremental uplift | Does not make budget or targeting decisions |
| **SHAP TreeExplainer** | Attributes the top 3 features driving each user's uplift score | Does not decide which users to target |
| **Deterministic optimizer** | Ranks users by uplift/cost efficiency and allocates budget greedily | No ML — pure business logic |
| **Gemini 2.5 Flash** (structured output) | Translates structured ML outputs into plain-language explanations and bilingual SMS copy | Never sees raw data, never makes financial decisions, never controls targeting logic |

### Step 6 — Impact
| Metric | Definition |
|---|---|
| **Incremental 30-day Active User Conversion Rate** | % of targeted dormant users who complete 3+ solo-utility transactions within 30 days *because of the offer* (uplift, not just response) |
| **Reactivation ROI per BDT Spent** | Incremental MAU gained ÷ total campaign spend in BDT |
| **Cashback Waste Saved** | BDT not spent on "Sure Things" who would have transacted anyway |
| **Fatigued Users Protected** | Count of users suppressed from receiving spam that would have caused negative uplift |

### Step 7 — Data
**100% synthetic.** No real upay user data is used at any point.

- 10,000 synthetic user records generated by `backend/data_generator.py` with seed `42`.
- 8,000 training rows (`data/train.csv`), 2,000 held-out test rows (`data/test.csv`).
- Stratified split by `treatment` × `lifecycle_stage` to preserve balance.
- Ground-truth uplift patterns are planted by the data generator (documented below in §3).

### Step 8 — Validation
1. **Train/test isolation:** Zero `customer_id` overlap between train and test sets (enforced by pytest).
2. **Uplift quadrant analysis:** Persuadables should show mean uplift > +15pp; Sleeping Dogs should show negative uplift.
3. **Budget constraint adherence:** Optimizer output `total_spend_bdt` must never exceed the input `budget_bdt`.
4. **Fairness audit:** Min/max contact-rate ratio across `lifecycle_stage` and `wallet_type` should exceed 0.7.
5. **Gemini fallback resilience:** System must return valid responses with `generation_source: "Offline Deterministic Fallback"` when no API key is set.

### Step 9 — Scale
- The budget optimizer is O(n log n) — dominated by the sort step. It can process upay's full 35M+ registered user base in seconds.
- LightGBM inference is O(n × trees × depth) — milliseconds per user, pre-computable in batch.
- SHAP values are pre-computed at training time and served from CSV — no real-time tree traversal.
- The Gemini API is called on-demand per customer view and per simulation, not in bulk.

## 2. Problem Statement

> For upay's growth and marketing team, high user dormancy and day-one salary cash-outs driven by competitor P2P network effects cause low Monthly Active User (MAU) retention and wasted mass-campaign spend. We will build upay ActivateAI, a lifecycle orchestration and uplift optimization engine that uses synthetic onboarding, transaction, and campaign response data to trigger personalized solo-utility offers within a fixed budget, with success measured by incremental 30-day active user conversion rate and reactivation ROI per BDT spent.

## 3. Synthetic Data Assumptions Log

All data is generated by `backend/data_generator.py` with `seed=42`. No real user data is used.

### 3.1 User Features

| Feature | Assumption |
|---|---|
| `lifecycle_stage` | Assigned based on behavioral rules: Sign-Up Drop-off (0 tx), Payday Cash-Outer (cashout_ratio > 0.90 and Salary wallet), One-Hit Wonder (1 historical tx), At-Risk Churner (inactive 21+ days, 2+ historical tx) |
| `wallet_type` | Distribution: Primary 50%, Salary 30%, Remittance 20% |
| `days_inactive` | Varies by lifecycle stage: Drop-offs 30–180, Cash-Outers 1–14 (they transact but only cash-out), One-Hit 14–90, Churners 21–120 |
| `historical_tx_count` | Drop-offs: 0; Cash-Outers: 5–30 (all cash-out); One-Hit: 1; Churners: 2–50 |
| `monthly_inflow_bdt` | Log-normal distribution, mean varies by wallet type (Salary: higher, Remittance: moderate, Primary: lower) |
| `cashout_ratio` | Cash-Outers > 0.90; others: beta distribution centered at 0.4 |
| `top_affinity_domain` | Roughly uniform across 4 domains, with slight wallet-type correlation (Salary users lean Utility_Bill, younger profiles lean Mobile_Recharge) |
| `promos_sent_30d` | Poisson(λ=2.5); fatigued users have λ=8+ |
| `promo_ignore_streak` | Correlated with promos_sent_30d; fatigued users have streaks of 5–12 |
| `channel_type` | 70% App, 30% USSD_268; USSD more common for Remittance wallet |

### 3.2 Planted Uplift Patterns

| Quadrant | Selection Criteria | P(activate \| treated) | P(activate \| control) | Planted Uplift |
|---|---|---|---|---|
| **Persuadables** | `days_inactive` 7–45, `historical_tx_count` > 2, affinity-matched offer | ~35% | ~8% | **≈ +27pp** |
| **Sure Things** | `days_inactive` < 7, `historical_tx_count` > 10 | ~40% | ~40% | **≈ 0pp** |
| **Lost Causes** | `days_inactive` > 90, `historical_tx_count` ≤ 1 | ~3% | ~3% | **≈ 0pp** |
| **Sleeping Dogs** | `promos_sent_30d` > 7, `promo_ignore_streak` > 5 | ~5% | ~10% | **≈ −5pp** |

### 3.3 Offer Economics

| Solo-Utility Offer | Mapped Affinity | Cost (BDT) |
|---|---|---|
| Zero-Fee Bill Pay + 30 BDT Cash Reward | Utility_Bill | 30 |
| 20 BDT Recharge Bonus | Mobile_Recharge | 20 |
| 10% Super Shop QR Cash Reward | Merchant_QR | 15 |
| Zero-Fee UCB ATM + Toll Pass Offer | Toll_Transit | 50 |

### 3.4 Treatment Assignment

- Randomized ~50/50 control/treatment split (simulated RCT).
- Assignment is independent of user features (unconfounded).

### 3.5 Activation Definition

A user is considered "activated" (`activated_30d = 1`) if they completed **3 or more solo-utility transactions within 30 days** of offer delivery. This is a habit-formation threshold, not a single conversion.

## 4. Responsible AI Checklist

### 4.1 Privacy
- [x] All data is 100% synthetic — no real upay user data, PII, or transaction records are used at any stage.
- [x] No real phone numbers, account numbers, or names appear in the dataset.
- [x] The Gemini API receives only synthetic structured summaries, never raw data.

### 4.2 Explainability
- [x] Every user-level recommendation is traceable to the **top 3 SHAP feature attributions** that drove the uplift score.
- [x] SHAP values are pre-computed at training time and stored alongside predictions for auditability.
- [x] Gemini-generated explanations are grounded in structured ML outputs — the LLM translates, it does not decide.
- [x] The `generation_source` field in every API response discloses whether the output came from "Gemini 2.5 Flash" or "Offline Deterministic Fallback".

### 4.3 Fairness
- [x] A fairness audit compares contact rates, mean uplift, and user counts across `lifecycle_stage` and `wallet_type`.
- [x] The audit flags any group where the min/max contact-rate ratio falls below 0.7.
- [x] Remittance wallet users (often rural, lower digital literacy) are explicitly monitored to ensure equitable offer allocation.
- [x] USSD_268 channel users are not systematically excluded from high-value offers.

### 4.4 Security
- [x] No API keys, secrets, or credentials are committed to the repository.
- [x] The `GEMINI_API_KEY` is loaded from `.env` (git-ignored) and is optional — the system functions without it.
- [x] The Gemini API is called via the official `google-genai` SDK with structured outputs, not raw HTTP.

### 4.5 Human Oversight
- [x] No campaign is dispatched automatically. The `POST /api/approve-campaign` endpoint requires a reviewer name, budget confirmation, and notes.
- [x] The frontend displays a `PENDING HUMAN APPROVAL` status badge until sign-off.
- [x] Campaign approval is logged with a timestamp and reviewer identity for audit trail.
- [x] The budget optimizer respects hard caps — it cannot exceed the approved budget under any input.
